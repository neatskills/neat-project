# Code Structure Design

Defines code structure decision framework for consistent project organization across tech stacks.

**Purpose:** Solutioning uses this reference to make strategic structure decisions, then applies generation rules to compute the actual folder structure.

---

## Inputs

Extracted by solutioning Phase 4 Step 3 (after the Architecture diagrams are written in Step 2) before applying the rules below.

**From PRD:**

- Project type: derive from PRD Requirements analysis (library if "publish to npm/pypi/crates", web-app if frontend, api-service if backend HTTP, cli if command-line)
- Tech stack: primary language/framework decided earlier in solutioning Phase 3 Gap Resolution (e.g., python, typescript, go)
- Ecosystem: backend | frontend | mixed (determined from project type and containers)
- Deployment model: from operational decisions in solutioning Phase 3
- Product count: from PRD § Products section (1 if section absent)
- Team structure: from PRD § Project Context
- Domain complexity: from PRD § Project Context (simple | moderate | complex — classified by assessing)
- Repository preference: from PRD § Project Context (if multi-product; absent if single product)
- Scale: active_requirement_count from PRD Delivery Estimate table
- `{mode} = Modernization` (no PRD): derive these from the loaded `modernization.md` sections. Ask the user for any input they do not state.

**From solution (this phase):**

- Container diagram → deployment units (count containers from "Owned containers" list), determine if mixed ecosystem (backend + frontend apps)
- Component diagram → modules/domains
- Domain count: count distinct business domains from Component diagrams

## Decision Rules

These rules determine the strategic structure decisions (WHAT pattern to use). The actual folder structure is then generated by applying the Generation Rules below.

### Rule 1: Repository Strategy

**Scale metric definition:** `scale := active_requirement_count` (from PRD Delivery Estimate table)

**Decision Tree:**

```
IF product_count > 1 AND repository_preference = "multi-repo"
  → multi-repo
  Rationale: Explicit user preference; separate teams, independent versioning

ELSE IF product_count > 1 AND repository_preference = "{inferred}" AND team_structure = "multi-team"
  → multi-repo
  Rationale: Multiple teams, no preference stated → default to independent repos

ELSE IF product_count > 1 AND (repository_preference = "monorepo" OR repository_preference = "{inferred}")
  → monorepo (workspace per product)
  Rationale: User preference OR single team managing multiple products → shared tooling

ELSE IF product_count = 1 AND (scale > 50 OR containers > 3)
  → monorepo (workspace per container/service)
  Rationale: Large single product benefits from modular workspace structure

ELSE IF product_count = 1 AND deployment_model = "microservices" AND containers > 1
  → monorepo (workspace per service)
  Rationale: Microservices in one repo — shared types, synchronized deploys

ELSE
  → single-repo
  Rationale: Default for moderate single-product projects
```

**Inputs Required:**

- `product_count`: from PRD § Products section (1 if section absent)
- `repository_preference`: from PRD § Project Context (only present for multi-product)
- `team_structure`: from PRD § Project Context (solo | small-team | multi-team)
- `scale`: active requirement count from PRD Delivery Estimate table
- `containers`: count from solution.md § Architecture § Container Diagram "Owned containers" list
- `deployment_model`: from solution.md § Operational Concerns

**Outputs:**

- `repository_strategy`: monorepo | multi-repo | single-repo
- `rationale`: Why this strategy fits the inputs

---

### Rule 2: Organization Pattern

**Decision Tree:**

```
IF domain_complexity = "complex"
  → feature-based
  Rationale: High domain complexity benefits from feature isolation

ELSE IF domain_complexity = "simple"
  → layer-based
  Rationale: Simple domain, clear separation of concerns

ELSE IF tech_stack IN ["next.js", "angular", "vue-cli"] (frontend with feature conventions)
  → feature-based
  Rationale: Framework conventions favor feature organization

ELSE IF tech_stack IN ["fastapi", "django", "spring-boot", "asp.net"] (backend with layer conventions)
  → layer-based
  Rationale: Framework conventions favor layered architecture

ELSE
  → layer-based (default)
  Rationale: Moderate complexity, standard architectural pattern
```

**Inputs Required:**

- `domain_complexity`: from PRD § Project Context (simple | moderate | complex — thresholds defined in `neat-discovery-assessing/references/scoping-method.md` § Domain Complexity Method)
- `tech_stack`: primary framework from solution.md Phase 3 Gap Resolution
- `domain_count`: count distinct business domains from Component diagrams
- `scale`: active requirement count

**Outputs:**

- `organization_pattern`: layer-based | feature-based | hybrid
- `rationale`: Why this pattern fits the domain and tech stack

**Hybrid Pattern:**

- Use when: frontend (feature-based) + backend (layer-based) in same repo
- Structure: workspace per app, each with its own pattern

---

### Rule 3: Module Boundaries

**For Monorepo:**

Determine workspace/package boundaries:

```
IF monorepo strategy = "workspace per product"
  → packages/{product-name}/ for each product
  → packages/shared/ for cross-product code

ELSE IF monorepo strategy = "workspace per container"
  → packages/{container-name}/ for each container
  → packages/shared/ for cross-container code

ELSE IF monorepo strategy = "workspace per service" (microservices)
  → services/{service-name}/ for each service
  → packages/shared/ for shared domain/contracts
```

**For Feature-Based:**

Identify feature areas from requirements (group by delivery objective):

```
Feature areas = GROUP requirements BY delivery_objective
For each feature:
  - Feature name: from requirement cluster
  - Responsibilities: requirements in this feature
  - Components: modules needed to deliver the feature
```

**For Layer-Based:**

Standard layers:

- **Backend:** domain, application, infrastructure, api
- **Frontend:** core, adapters, ui

**Multi-domain handling:**

- **Layer-based:** domains_within_layers (domain/pipeline/, domain/monitor/)
- **Feature-based:** domains_as_top_level (pipeline/domain/, monitor/domain/)

**Inputs Required:**

- `organization_pattern`: from Rule 2
- `repository_strategy`: from Rule 1
- `containers`: from solution.md Container Diagram
- `requirements`: from PRD or `requirementsNN.md`
- `components`: from solution.md Component Diagrams

**Outputs:**

- Module boundary table:
  - **Monorepo:** Package/Module | Purpose | Depends On
  - **Feature-based:** Feature Area | Requirements | Components
  - **Layer-based:** Layer | Responsibility | Key Components

---

### Rule 4: Monorepo Tool Selection

**Decision Tree (if repository_strategy = monorepo):**

```
IF tech_stack = "typescript" OR "javascript"
  IF need_incremental_builds OR scale > 30 requirements
    → turborepo OR nx
    Rationale: Large TS projects benefit from build caching
  ELSE
    → pnpm-workspaces OR npm-workspaces
    Rationale: Simple workspace management sufficient

ELSE IF tech_stack = "python"
  → poetry-workspaces
  Rationale: Poetry handles Python monorepo dependencies

ELSE IF tech_stack = "go"
  → go-modules
  Rationale: Native Go workspace support (go.work)

ELSE
  → none (language-native approach)
  Rationale: No specialized tooling needed
```

**Inputs Required:**

- `tech_stack`: from solution.md Phase 3 Gap Resolution
- `scale`: active requirement count
- `need_incremental_builds`: true if >5 packages OR frequent interdependency changes

**Outputs:**

- `monorepo_tool`: pnpm-workspaces | npm-workspaces | turborepo | nx | poetry-workspaces | go-modules | none
- `rationale`: Why this tool fits the tech stack and scale

### Folder Tree Assembly

Combine all applied rules to construct the complete folder structure:

1. Start with root structure (Rule 5)
2. Add repository strategy layout (Rule 6 if monorepo, otherwise single-repo layout)
3. Add organization pattern layers (Rule 1)
4. Add layer substructure (Rule 3)
5. Add multi-domain structure (Rule 2)
6. Apply naming conventions (Rule 7)
7. Add tech stack configs (Rule 4)
8. Apply framework-specific structure (Rule 8 if applicable)

Output: Folder tree with actual names (no placeholders), showing 3-4 levels deep.

**Name mapping:**

| Concept | Source | Transformation |
| --- | --- | --- |
| project-name | PRD project name OR repo directory | Apply Rule 7 naming_convention |
| package-name | Python: project_name (snake_case) | Apply Rule 7 for python |
| app-name | Container name from C4 Container | Apply Rule 7 naming_convention |
| product-name | PRD § Products | Apply Rule 7 naming_convention |
| domain-name | Component diagram domains | Apply Rule 7 naming_convention |
| module-name | Component name | Apply Rule 7 naming_convention |

## Brownfield Migration

When refactoring an existing flat structure to a layered or feature-based structure:

### Migration Strategy Decision

**Gradual Migration (recommended for production systems):**

- Create target folders alongside existing flat structure
- Move files incrementally in phases (grouped by layer or feature)
- Test after each phase
- Commit after each successful phase
- Delete old structure only when fully migrated

**Restructure Upfront (for greenfield or paused projects):**

- Create complete target structure
- Move all files at once
- Update all imports
- Test comprehensively
- Commit

### Migration Phases

Example for layer-based migration (Python backend):

**Phase 1 — Core Domain:**

1. Create core/, core/domain/, core/services/
2. Move domain models and business logic
3. Update imports in moved files
4. Update imports in files that reference moved files
5. Run tests → commit

**Phase 2 — Adapters:**

1. Create infrastructure/ or adapters/
2. Move repository interfaces, external API clients
3. Update imports → test → commit

**Phase 3 — API Layer:**

1. Create api/, api/routes/
2. Move controllers, FastAPI app
3. Update imports → test → commit

**Phase 4 — Cleanup:**

1. Verify all files migrated
2. Delete empty root files
3. Final test suite → commit
