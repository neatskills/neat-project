# Structure Checks

## Skeleton Creation

### Pre-check — Brownfield detection

Scan for: `src/`, `app/`, `lib/`, `internal/`, `pkg/`, `cmd/` OR package manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile`, `pom.xml`, `build.gradle`, `*.csproj`, `composer.json`)

**No existing structure (greenfield):** Proceed to skeleton creation.

**Existing structure found:**
- List detected directories and manifests
- Ask user:
  > [1] Merge (create alongside existing, skip existing dirs)
  > [2] Error out (stop, escalate)
  > [3] Show diff (compare detected vs planned, then re-ask)

### Skeleton steps

1. **Read structure plan:**
   Load `specs/discovery/solution.md § Code Structure § Folder Structure`.
   For multi-repo: read all repository subsections.

2. **Parse folder tree:**
   Extract directory paths from code block.
   Validate: paths must be relative, no placeholders like `{name}`.
   If validation fails: escalate to planning with issue "Structure contains placeholders or absolute paths"

3. **Create skeleton:**
   For each directory in tree:
   - Check if directory already exists (brownfield merge case)
   - If not exists: `mkdir -p {path}`
   - If README mentioned in § Conventions: create stub README.md (skip if exists)

4. **Initialize configs:**
   If `§ Conventions` specifies config locations:
   - Create config directory (if not exists)
   - Add `.gitkeep` or stub config files as appropriate (skip if exists)

   If monorepo tooling specified in solution.md § Code Structure § Repository Strategy:
   - Initialize workspace config based on monorepo tool:
     - JavaScript/TypeScript:
       - `pnpm-workspaces`: create `pnpm-workspace.yaml`
       - `npm-workspaces`: update `package.json` with workspaces field
       - `yarn-workspaces`: update `package.json` with workspaces field
       - `turborepo`: create `turbo.json`
       - `nx`: create `nx.json` and `workspace.json`
       - `lerna`: create `lerna.json`
     - Python:
       - `poetry-workspaces`: create `pyproject.toml` with tool.poetry.workspaces
     - Go:
       - `go-modules`: no config needed (uses go.work if multi-module)
     - Rust:
       - `cargo-workspaces`: update `Cargo.toml` with workspace config
     - Generic:
       - No tooling specified: proceed with directory structure only

5. **Validate:**
   List created directories.
   Confirm structure matches solution.md tree.
   Record in session state: `structure_skeleton_created = true`

## Placement and Layer Validation

### Placement validation

1. **Determine target path:**
   Based on file type and structure from solution.md § Code Structure:

   Load `specs/discovery/solution.md § Code Structure § Organization Pattern` to determine if layer-based, feature-based, or hybrid.

   **If layer-based:**
   - Domain model/entity → `{domain-layer-path}` (from § Folder Structure)
   - Service/use-case → `{application-layer-path}`
   - Repository/adapter/external client → `{infrastructure-layer-path}`
   - Controller/handler/route → `{api-layer-path}`
   - Test → `{test-path}` from § Conventions
   - Config → `{config-path}` from § Conventions

   **If feature-based:**
   - Feature code → `{feature-area-path}/{component-type}/` (from § Module Boundaries table)
   - Shared utilities → `{shared-code-path}` from § Conventions
   - Test → co-located `__tests__/` or per § Conventions
   - Config → `{config-path}` from § Conventions

   **If hybrid:**
   - Follow hybrid strategy from § Organization Pattern

2. **Validate against skeleton:**
   - Parent directory exists in skeleton → proceed
   - Parent directory missing → escalate to planning — issue: "Structure incomplete: missing directory {path}"

3. **Generate into correct location.**

### Cross-layer validation (layer-based only, run AFTER generating each file)

**Dependency rules:**

- Domain files MUST NOT import from application/infrastructure/api
- Application MAY import from domain only
- Infrastructure MAY import from domain + application
- API MAY import from all layers

**Validation approach:**
After each implementation task completes:

1. Select up to 3 files generated by this task (or all if <3 files)
2. Read each file's import statements
3. Check against dependency rules above
4. If violations found → flag and ask user:
   > Layer boundary violation detected in {file}:
   > {layer} imports from {forbidden-layer}
   >
   > [1] Fix imports (refactor)
   > [2] Accept violation — write `debt` entry to issues.md
   > [3] Discuss

## Wave Structure Validation

Validate all files created during this wave's build against solution.md § Code Structure:

1. **Placement check:**
   - All files in `touched_files` placed per solution.md § Code Structure
   - No files created outside defined structure
   - If violations found → record in `**Deviations:**` for Phase 6

2. **Layer boundary check (layer-based only):**
   - Layer boundaries respected per dependency rules (§ Placement and Layer Validation above)
   - If violations found AND not already flagged in Phase 2 Step 4 → record in `**Deviations:**` for Phase 6

3. **Conventions check:**
   - Tests in correct location per § Code Structure § Conventions
   - Configs in correct location per § Code Structure § Conventions
   - If violations found → record in `**Deviations:**` for Phase 6
